# PKUBA 系统规范

本文是新版 PKUBA 的稳定系统说明。规则优先级、开发接手和发布流程分别见
[`AGENTS.md`](../AGENTS.md)、[`MAINTAINER_GUIDE.md`](MAINTAINER_GUIDE.md) 与
[`WORKFLOW.md`](../WORKFLOW.md)。专题细节由本目录下的调赛、赛程导入、记录表、
API 可靠性、备份恢复和部署规范定义。

## 系统边界

- Django/PostgreSQL 是唯一业务权威；管理站和微信小程序不自行推导权限或状态。
- 旧小程序、历史脚本和旧工作簿只用于理解来源，不是兼容实现或上线入口。
- 正式入口为 `admin.pkuba.cn`、`api.pkuba.cn` 和微信小程序；根域名跳转管理站。
- API、数据库、媒体、归档、OpenAPI、生成客户端和两端页面必须保持同一版本合同。

## 身份与权限

- 角色包括普通用户、领队、管理员和超级管理员；双身份账号按当前入口取得相应能力。
- 微信交换、网页扫码和网页密码登录均由服务端建立会话，客户端不得上传完整身份对象。
- 管理员不能执行超级管理员专属操作；归档赛季默认只读，纠错必须走专用确认和审计。
- 空库首位超级管理员只通过一次性交互命令创建。命令拒绝既有超级管理员、同名账号、
  非交互密码和并发创建；后续账号全部使用产品内正式流程。

## 赛季、球队与赛程

- 赛季有 SETUP、PUBLISHED、ARCHIVED 生命周期；所有专属记录在数据库层隔离。
- 赛事组别、球队、名单、场地、时段、容量、签位和比赛状态均由服务端校验与审计。
- 唯一导入合同是 V3.3；也可使用在线草稿。旧 V1/V2、特定赛季导入器和 demo seed
  不属于系统。
- 赛程导入先预览，再以版本和确认摘要提交；失败原子回滚。在线草稿同样绑定版本。
- 容量只保留当前数值，不保存已退役的历史推断来源；签位校验值只使用当前枚举。
- 公开统计只读取正式比赛结果；VOID 不公开，FORFEIT、COMPLETED 按规则计算。

## 调赛

- 日期关系 `SAME_WEEK`/`CROSS_WEEK` 与处理通道
  `ORDINARY`/`HANDBOOK_REVIEW` 是独立语义。
- 普通入口只接受同周普通调赛；手册入口可提交同周或跨周，并进入超级管理员审核。
- 目标场地在正式批准前只用于服务端预留和冲突检查，不向参与者泄露。
- 确认、预留、Inbox、Outbox 和审计与状态机处于同一事务；失败不留部分写。
- 淘汰赛 `game.group = NULL` 时，指定球队确认候选为同一赛事组别全部启用球队，排除
  比赛双方，由超级管理员精确选择。

## 媒体、记录表与统计

- 比赛媒体先进入暂存，校验后晋升；文件大小与 SHA-256 必须和数据库一致。
- 每场记录表保留唯一当前来源，同时永久保留历史来源证据、识别 run、人工草稿、修订、
  publication 和审计。
- 自动识别失败且尚未发布时可人工编辑后重试；重试前明确提示整稿覆盖，成功覆盖、失败
  保留旧稿。已发布或已成功识别的记录不开放任意重识别。
- 比赛上下文发生变化时保留原图和人工内容。非实质变化经服务端复核后可继续发布；球队、
  日期、场地、名单等实质差异必须展示并由有权管理员重新确认。
- 得分、犯规、球员身份、比赛结果和排行榜由当前权威名单与规则重新校验。publication
  不可变，纠错生成新 publication，不改写旧版本。

## API 与失败合同

- 写请求使用稳定 ID、当前版本和必要的 `Idempotency-Key`；未知结果使用原键和原上下文
  核实，不自动换键重复写入。
- 权限、校验、状态和并发冲突返回可识别的 4xx/409；意外错误返回 5xx 且不得泄密。
- 分页、错误、安全重试和生成客户端合同见 [`API_RELIABILITY.md`](API_RELIABILITY.md)。
- 只读请求不悄悄写入确认状态；异步旧响应不得覆盖更新的身份、页面或业务上下文。

## 归档、备份与恢复

- 赛季数据和照片归档由正式任务生成，文件、清单、摘要与哈希一致后才标为 READY。
- 生产数据库、媒体和归档必须在 writer fence 内形成配对一致恢复点。
- 应用故障只回切应用，绝不恢复数据；只有确认数据损坏才执行成对恢复。
- 发布事务、完成审计、掉电恢复、writer fence 和保留策略见
  [`DEPLOYMENT.md`](DEPLOYMENT.md) 与 [`BACKUP_AND_ARCHIVE.md`](BACKUP_AND_ARCHIVE.md)。

## 生产拓扑与发布

- 生产根目录为 `/opt/pkuba/production`；Compose project 为 `pkuba-gateway`、
  `pkuba-data`、`pkuba-blue` 和 `pkuba-green`。
- 数据卷固定为 `pkuba-prod-postgres`、`pkuba-prod-media`、`pkuba-prod-archives`；Caddy
  数据与配置使用独立 `pkuba-prod-*` 卷。
- PostgreSQL、Caddy、API 和 Web 镜像都使用审核过的 GHCR digest；release manifest
  记录来源 digest、镜像 digest、tag 和 commit。
- 生产首次启动只允许空数据库；迁移后一次性创建首超管，再由产品流程配置赛季。
- 生产发布必须经过受保护 main、版本标签、required CI、独立验收、Environment 审批、
  HTTPS 稳定入口核验和已演练的回滚/恢复路径。
