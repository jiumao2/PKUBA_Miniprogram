# 调赛状态机与兼容规范

本文是新版 PKUBA 调赛实现的专题规范。用户操作说明见 `USER_GUIDE.md`；旧系统事实见根目录功能规格。

## 三个独立概念

| 概念 | 持久化字段 | 含义 | 决定者 |
| --- | --- | --- | --- |
| 日期关系 | `request_type` | 原日期与目标日期是否属于同一 ISO 自然周 | 服务端按日期计算 |
| 处理通道 | `process_route` | 对手同意后自动生效，或进入《参赛手册》审核 | 领队选择入口，服务端复核 |
| 审核认定 | `review_classification` | 管理员最终认定为按普通办法或跨轮次调整 | 超级管理员 |

`request_type` 只表达日期关系，不再决定处理通道。客户端不得提交或覆盖日期关系。

## 两个领队入口

- **普通调赛**提交 `ORDINARY` 通道，只返回原比赛同一自然周的合法目标。
- **跨周调赛**提交 `HANDBOOK_REVIEW` 通道，同时返回同周和跨周的全部合法目标。
- 两个入口允许出现相同的同周目标；入口决定处理通道，而不是由目标日期反推用户选择。
- 跨周入口首屏必须说明：“可选择本周或跨周时段，是否跨轮次由管理员审核”。
- 若手册审核通道选择了同周目标，对手同意后仍等待超级管理员认定，不能自动生效。

创建事务重新计算日期关系，并复核权限、版本、截止时间、容量、球队冲突和场地预留。`ORDINARY + CROSS_WEEK` 永远非法；省略通道的旧客户端仅可按日期关系安全推断，同周为普通、跨周为手册审核。

## 状态迁移

1. 创建后进入“等待对手”，原比赛锁和目标预留同时生效。
2. 对手拒绝或超时：申请结束，并在同一事务释放锁与预留。
3. 对手同意：
   - `ORDINARY + SAME_WEEK`：原子批准并更新正式赛程。
   - `HANDBOOK_REVIEW` 或任何 `CROSS_WEEK`：进入“等待管理员决定”。
4. 超级管理员必须先记录审核认定：
   - 同周申请可认定“按普通办法”，直接批准，无需领队重提。
   - 认定“跨轮次调整”后，可直接批准、拒绝或指定球队确认。
   - 跨自然周申请不能认定为“按普通办法”。
5. 指定球队全部按时同意后进入“等待管理员终审”，之后不因管理员尚未处理而自动过期。
   - 小组赛等具有小组归属的比赛：候选仅限同小组内除比赛双方外的启用球队。
   - 淘汰赛等无小组归属的比赛：候选扩大为同赛事组别内除比赛双方外的全部启用球队，不按主队原小组推断。
   - 超级管理员从服务端返回的候选中精确选择；提交时服务端在事务内按同一规则重新校验。
6. 所有非终态持续持有原比赛锁和目标预留；批准时预留转为正式占用，其他终态幂等释放。

## 权限、并发与审计

- 所有命令按 request ID 重新加锁读取，校验账号、当前状态和 `expected_version`。
- 陈旧版本返回 `409`；非法通道、分类或动作返回稳定 `400`；失败事务不得留下分类、确认、审计或资源部分写入。
- 管理员审核审计同时保存日期关系、处理通道、审核认定、前后状态和指定球队。
- 任务箱和公邮使用“日期关系 / 处理通道 / 审核认定”的用户可读文案；未生效场地始终隐藏。

## Expand / contract 兼容

0039 是保守的 schema expand，不等于旧应用具备新业务语义。字段暂允许为空，使迁移可以解释迁移前记录，也使数据库能够对旧写入 fail closed；它不授权 `bf444ece` 之类只理解 `request_type` 的应用继续接流量。

- 历史空值按可证明事实解释：同周默认为普通通道；跨周默认为手册审核；只有管理员审计、VOTER 确认或既有投票/终审状态能证明时才回填“跨轮次调整”，不能凭空伪造审核结论。
- `SAME_WEEK + HANDBOOK_REVIEW` 是新语义。旧应用会在对手同意后尝试按普通流程自动批准；数据库约束会让整笔事务回滚，但旧端点可能表现为 5xx。因此旧应用不是安全共存栈，也不是功能激活后的普通回切点。
- 首次启用必须采用能力分阶段：先部署理解 `process_route`、分类与新幂等指纹但尚未开放新入口的 bridge 版本。在同一个 writer fence 内停止旧 API/worker 写入，完成 0039 及历史证据审计，再运行 `python manage.py reschedule_route_activation_preflight --wait-seconds=86400 --json`，直到所有非终态调赛申请和仍在 24 小时有效期内、响应不含 `process_route` 的旧幂等记录均为 0；确认两个可回切 slot 都声明并通过对应 capability contract；之后才开放同周手册通道并切流。当前仓库尚未实现这条 baseline conversion 自动脚本，测试阶段只能在隔离环境演练，不能把独立 management command 写成已自动接线的发布门禁。
- 处理通道激活后，只能回切到保留状态中明确记录“允许从当前 capability 回切”的应用。仅能读取 nullable 列、或只拥有旧 `request_type` 语义的版本不得接流量。
- 旧幂等记录的 digest/响应正文不与新协议伪装成完全兼容。激活前必须等待其服务端 TTL 到期或通过受审计的一次性转换清空对应窗口；新协议内部的缺省/显式同义 payload 才使用归一后的业务指纹重放。
- 确认没有空值、旧应用和旧幂等窗口后，再用独立 contract 迁移将字段设为非空并删除临时兼容分支。

## 必测场景

- 普通入口不返回跨周目标；手册入口同时返回同周和跨周目标。
- 手册入口的同周申请不自动生效，管理员可按普通办法直接批准。
- 跨周目标不能通过缺省值或伪造 `ORDINARY` 降级。
- ISO 周跨月、跨年边界按 `date.isocalendar()` 判定。
- 分类与动作非法、版本陈旧和并发处理均零部分写。
- 迁移前非法历史投票状态、未知枚举或缺少 VOTER 证据会原子阻断 0039，不会被迁移“合法化”。
- 新同周手册申请遇到旧应用误自动批准时，数据库 fail closed，确认、申请、比赛、预留、任务、邮件和审计均零部分写。
- capability/feature-activation 门禁在 Compose、停服和数据库/媒体/归档访问前拒绝不理解新通道的旧版本。
- 激活预检会动态拒绝全部非终态调赛申请和仍有效的旧版 `reschedule.create` 幂等响应；过期或已包含新通道字段的记录不会误阻断。检查必须位于旧写入已停止的同一围栏内，不能先检查再允许旧栈继续写入。
- 只有 capability contract 明确允许的保留栈可在 24 小时窗口内执行 application-only 回切；数据库、媒体与归档均不恢复。
