# 记录表识别、跨端审核与统计发布

本模块把每场比赛的纸质记录表原图、结构化草稿、人工编辑、正式发布和公开统计纳入同一套 Django/PostgreSQL 权威数据。旧小程序与原 `ScoresheetReader` 仓库保持只读，运行时不读取其目录，也不保存网页端或小程序端的独立业务副本。电脑端编辑器以 `ScoresheetReader` 提交 `c27fe987a71637a8f1161a991d3c15f6c0afdeed` 为冻结基线，将其完整工作台、领域模型、校验、模板坐标和 PDF 渲染迁入本仓库；电脑端不得另行改造原有编辑方式或删减功能。

## 权限与唯一性

- 普通管理员：首次发布前可上传、重传/替换来源、编辑、完整手工录入、在四次识别耗尽后发起新一轮识别、服务端校验并首次发布；已发布后只读。
- 超级管理员：拥有全部首次发布能力，并可在已发布后重传、纠错、强制接管和重新发布；旧 publication 在新版本成功发布前继续对外。
- 本场任一参赛球队领队：只能查看当前 publication 绑定的原图。纠错重传期间仍看到旧发布原图。
- 公众：只能读取当前 publication 生成的球队和球员统计。
- `Game` 与 `GameScoresheet` 一对一；数据库同时约束每场只能有一张未软删除的 `SCORESHEET` 原图。重传会新建来源并软删除旧来源，旧文件、识别任务、publication 和审计不覆盖。

## 状态与工作流

```text
上传完整单页原图
  -> RECOGNITION_QUEUED / RECOGNIZING
  -> RETRY_WAIT（如可重试）
  -> DRAFT 或 RECOGNITION_FAILED
  -> 人工编辑并保存
  -> 服务端校验、一次确认全部 warning
  -> READY
  -> PUBLISHED
```

`SOURCE_GAME`、`TEAM_A`、`TEAM_B`、`RUNNING_SCORE`、`SUMMARY`、`OFFICIALS` 只用于问题定位、识别差异和小程序步骤导航，不是电脑端发布前需要逐区点击的确认门槛。服务端会把前端整表自动保存拆成字段级变更日志。识别执行或等待自动重试期间所有客户端只读，且没有用户停止或重复启动接口；四次耗尽或凭据缺失后，普通管理员与超级管理员都可取得租约完整手工填写，四次耗尽后也可发起新的四次识别周期或重传新原图。名单缺失、图片非法等来源前置错误必须先修复来源。

## Qwen 识别与重试

识别 worker 使用 PostgreSQL 行锁、`skip_locked` 和五分钟 worker 租约，不依赖 Redis/Celery，也不在 Gunicorn 进程内执行模型请求。一次来源固定最多四次调用：首次加三次自动重试。

| 失败次数 | 下一次等待 |
| --- | --- |
| 第 1 次 | 30 秒 |
| 第 2 次 | 30 秒 |
| 第 3 次 | 30 秒 |
| 第 4 次 | 进入 `RECOGNITION_FAILED` |

网络错误、超时、HTTP 429/5xx、服务商无效 JSON 和结果 Schema 错误可重试。服务商 `Retry-After` 更长时采用更长时间。来源缺失/替换、名单缺失、图片不合法和凭据缺失不会重复调用。

发送给 Qwen 的内容严格限定为：安全解码、EXIF 纠正、约 6.3 MP 上限并以 JPEG 95、4:4:4 重新编码后的完整记录表，以及双方球队名称和球员姓名。不会发送账号、OpenID、UUID、球衣号码、赛季、日期、场地或其他比赛先验。默认使用 `qwen3.8-max`、`xhigh`、高分辨率视觉与 thinking、`seed=1234`、原版动态名单枚举 Schema 和严格结构校验。每个任务记录真实模型、提示词版本、处理后图像 SHA-256、token、来源版本和入队草稿版本；来源被替换时结果标记为 `SUPERSEDED`，人工已修改草稿后成功结果只进入差异面板，不自动覆盖人工输入。

本地与生产环境变量：

```dotenv
QWEN_API_KEY=
QWEN_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
QWEN_MODEL=qwen3.8-max
QWEN_REASONING_EFFORT=xhigh
QWEN_TIMEOUT_SECONDS=180
SCORESHEET_RECOGNITION_MAX_PIXELS=6291456
```

未配置 `QWEN_API_KEY` 时，worker 会把任务一次性标记为不可重试失败，页面仍可进入人工录入。生产 worker：

```bash
python manage.py process_scoresheets --poll-seconds 2
```

## 编辑租约与两秒同步

- 有写权限时打开编辑器取得 60 秒租约；自动识别执行或等待重试时所有人只读，终态成功、耗尽失败或凭据缺失后按权限自动取得租约，网页和小程序每 15 秒心跳。
- 同一时刻只有租约持有账号、客户端 ID 和端类型可写。网页每个标签页使用独立 `sessionStorage client_id` 和租约令牌，同一标签页刷新可恢复，不同标签页互不轮换令牌。获取、心跳、同步和释放均使用单飞锁；其他端每 2 秒轮询并保持只读。
- 保存、校验、warning 确认和发布都提交 `expected_version`、`lease_token`、`client_id`、`surface`。
- 两端不显示“接手、交接、强制接管”按钮。首个打开且有权限的终端自动取得编辑权；正常返回和发布先排空自动保存再释放，租约释放或 60 秒失效后，仍在前台的只读端在下一轮同步中自动取得编辑权。
- 服务端仍严格拒绝旧 token；超级管理员的已发布纠错权限和强制接管审计能力保留为受保护的服务能力，不在普通编辑界面暴露手工租约控制。
- 回到前台或网络恢复时立即同步。若本地草稿所基于的服务器版本未变化，可重新取得租约后恢复保存；若已变化，两端列出差异字段并要求明确选择服务器值或本地值。
- 撤销/重做作为普通服务端修改保存。网页保留最近 50 步会话历史；本地历史本身不替代服务端修订。
- 编辑器“人工修改记录”只返回人工编辑、撤销、重做、应用识别差异、重传和发布，并以中文摘要、稳定语义路径以及真实“修改前 → 修改后”值展示。租约、心跳、过期、识别 worker、校验和同步事件仍保留在数据库和高级数据页，不进入该列表；历史记录不删除，也不补造早期未保存的修改前值。

## 编辑器

电脑端从比赛资料进入独立的全视口 `scoresheet.html`，完整保留冻结版 `ScoresheetReader` 的布局、字段编辑、覆盖层、原图/PDF 对照、缩放旋转、检查器、撤销重做、识别差异、保存、校验和确认交互。PKUBA 适配层只替换数据与认证接口，并补入自动租约、750 ms 自动保存和两秒同步，不重新设计其编辑操作。

小程序编辑器位于独立分包，不使用 PDF.js 或 `web-view`。它按“原图、比赛信息、A 队、B 队、逐次得分、结表信息、校验发布”顺序审核，一次只显示原图或标准表。原图未选四角时不显示定位框；按左上、右上、右下、左下完成对齐后，才用模板坐标标出当前区域。对齐只用于人工查看，不裁切模型输入。

逐次得分按 `1-40`、`41-80`、`81-120`、`121-160` 四块显示。录入只允许球队当前累计分之后的 `+1/+2/+3`，快捷录入后自动切块和滚动；事件抽屉可改球员、分值、节次、节末/终场标记或删除。系统计算累计、节比分和最终比分但只作对照，不覆盖纸面输入；不一致交给服务端校验。

## 校验与发布事务

发布前同时检查：

- 当前来源、草稿、名单先验和比赛先验与校验报告摘要一致；
- error 为零；如存在 warning，发布前只弹出一次确认，确认后服务端一次性记录当前全部 warning；
- 当前客户端仍持有租约；
- 逐次得分、纸面累计、逐节比分和最终比分一致，正式比分不为平局；
- 冻结名单、首发/出场、队长、犯规、暂停、全队犯规、终场标记和工作人员字段满足当前 Schema/FIBA 2024 规则。

单一数据库事务创建不可变 `ScoresheetPublication`、`GameTeamStat`、`GamePlayerStat`，更新比赛正式比分和状态，把来源标为已通过，写修订/变更/管理员审计并释放租约。任一步失败都会回滚。弃权继续使用既有超级管理员 20:0 流程，不创建普通记录表 publication。

首次发布自身递增的 `Game.version` 会同步回记录表比赛先验，因此超级管理员可以在同一原图上修正草稿、重新校验并生成下一 publication；独立的赛程修改仍会使先验失效并要求重新上传或重新校验。已有 publication 的比赛不能再从通用赛程编辑器直接改比分或赛果，必须从记录表工作台重新发布。公开页与 CSV/XLSX 始终读取当前 publication 的快照名称、比分和统计，不读取以后可能变化的 `Game` 分数或球队名称。

## 公开统计与导出

公开数据只来自当前 publication：

- 球队：逐节/全场得分、胜负、暂停和全队犯规。
- 球员：出场、首发、得分、1/2/3 分事件数、个人犯规数及类型。

不推导命中率、篮板、助攻、抢断、盖帽、失误、上场时间或正负值。管理员编辑器的 PDF 始终渲染当前服务端草稿（包括已发布后的未再发布纠错）；公众展示和单场 CSV/赛季 XLSX 始终读取当前 publication。

## 本地双端编辑演示数据

`ScoresheetReader` 仓库没有可迁移的真实比赛原图或私有识别结果；可复用的数据是其公开合成测试夹具。新版提供一个显式、幂等的管理命令，把这份夹具转换为当前 Schema，并生成一张与其对应的纸面式 JPEG：

```bash
python manage.py seed_scoresheet_demo --confirm-local-demo --actor <superadmin-username>
```

命令只创建非公开的 `PKUBA 记录表编辑器演示` 赛季，不切换、归档或修改当前公开赛季。为了让真实租约和保存服务可用，它会把该隔离赛季的唯一演示组别标记为可操作；这是显式命令创建的本地测试例外，不是正式赛季上线流程。演示比赛固定显示为“示例学院甲 vs 示例学院乙”，开赛时间为 `12:50`；草稿直接移植公开 `synthetic_fixture.py` 的 1.4 语义，包含双方各 12 人、执照号、正式及纸面后置犯规、暂停、19 条逐次得分、四节比分、最终 `21:18`、工作人员和签名。识别任务按一次成功写入相同的 revision、事件和审计链，适合在网页和小程序之间实际测试自动只读、自动取得编辑权、保存、两秒同步、校验和发布。

默认管理员记录表队列继续列出公开赛季全部比赛，同时会额外列出已有记录表的非公开演示比赛；没有记录表的其他非公开赛季比赛不会混入队列。小程序卡片只展示日期、开赛时间、组别和双方，不展示内部比赛代码或 UUID。

## 私有文件、COS 与备份

当前部署仍使用 Django `default_storage` 的私有本地 Docker volume；文件只能通过短期签名票据接口读取。仓库中的 `COS_*` 变量是迁移预留项，尚未配置 COS storage backend，不能仅填写变量就宣称已上云。

启用腾讯云 COS 前必须完成并验证：私有 bucket、最小权限服务账号、服务端 SDK/storage backend、现有 `file_key` 原样迁移、对象数量与 SHA-256 清单核对、短期读取链路、失败回滚和本地副本保留期。API 与 worker 必须使用同一 storage backend；bucket 不得公开读，也不得把长期 COS 凭据写入小程序或网页。

生产备份必须把 PostgreSQL 和私有媒体视为同一个恢复点。建议在停止上传/发布的维护窗口执行：

1. `pg_dump --format=custom` 导出数据库，并记录 SHA-256。
2. 以只读方式归档 `private-media` volume，记录文件数、总字节数和归档 SHA-256。
3. 将数据库、媒体归档和清单复制到独立存储；至少保留一份异地副本。
4. 每月至少在隔离环境演练一次恢复：先恢复数据库，再恢复同一批次媒体，检查随机文件 SHA-256、记录表原图读取、PDF/CSV/XLSX 导出和当前 publication。

不要只备份数据库：publication 会保留来源外键，但缺少对应私有对象时领队无法查看已发布原图，识别重跑也无法读取来源。不要在生产库上直接演练恢复或删除旧来源文件。


真实管理站 Playwright 场景需要先设置 `PKUBA_E2E_USERNAME` 与
`PKUBA_E2E_PASSWORD`，再执行 `npm --workspace @pkuba/admin-web run test:e2e`。
设置 `RUN_PRIVATE_LIVE_UI=1` 会启用双标签租约与两秒同步场景；只有服务端已配置
Qwen 凭据时才设置 `RUN_SCORESHEET_RECOGNITION_E2E=1`，该开关会真实重传照片并
产生模型调用费用。未配置凭据时，真实照片识别场景应明确跳过，其余编辑、日志、
撤销/重做、画布、校验、发布、PDF 与双标签同步场景仍必须通过。
