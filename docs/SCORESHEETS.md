# 记录表识别、跨端审核与统计发布

本模块把每场比赛的纸质记录表原图、结构化草稿、人工编辑、正式发布和公开统计纳入同一套 Django/PostgreSQL 权威数据。旧小程序与原 `ScoresheetReader` 仓库保持只读，运行时不读取其目录，也不保存网页端或小程序端的独立业务副本。电脑端编辑器以 `ScoresheetReader` 提交 `f17b26e82cf3cd2d4878463e03c0580bd271fc31` 为冻结基线，将其完整工作台、领域模型、固定累计分格派生语义、校验、模板坐标和 PDF 渲染迁入本仓库；识别图片准备与 Qwen 请求模式以提交 `d631601` 为基线。电脑端不得另行改造原有编辑方式或删减功能。

## 权限与唯一性

- 普通管理员：首次发布前可上传、重传/替换来源、编辑、完整手工录入、在四次识别耗尽后发起新一轮识别、服务端校验并首次发布；已发布后只读。
- “已发布后”以本场存在任何 publication 为准，不因超级管理员换图后回到草稿或当前 publication 指针为空而恢复普通管理员重传权限。来源替换在接收和文件晋升事务中都重新校验；旧来源、正式统计和发布历史保持不变。
- 超级管理员：拥有全部首次发布能力，并可在已发布后重传、纠错、强制接管和重新发布；旧 publication 在新版本成功发布前继续对外。赛季归档后只允许网页端明确确认的已有 publication 纠错，不开放新建记录表、照片修改或小程序编辑。
- 本场任一参赛球队领队：只能查看当前 publication 绑定的原图。纠错重传期间仍看到旧发布原图。
- 公众：只能读取当前 publication 生成的球队和球员统计。
- `Game` 与 `GameScoresheet` 一对一；数据库同时约束每场只能有一张未软删除的 `SCORESHEET` 原图。重传会新建来源并软删除旧来源，旧文件、识别任务、publication 和审计不覆盖。

媒体列表的 `can_replace` 与记录表队列、详情、同步响应的 `can_upload_source` 使用同一服务端权限判断。网页和小程序据此显示上传/重传入口，不从草稿状态、当前图片是否就是已发布来源或是否持有编辑租约推断；缺少授权字段按不可上传处理。选择文件后仍核对当前记录与权限，服务端保留最终写入保护。原图查看、缩放和重新载入不受上传权限限制；合照和其他照片的原有操作不变。

网页同步同时绑定打开代次、草稿/事件水位和最近一次权威详情读取。发布可以只推进事件，角色变化可以不推进草稿或事件；在新读取之前发出的共享请求均不得恢复旧权限。详情 GET 按发起顺序与服务端水位判定新旧，旧响应及等待租约后的旧续接不得覆盖已知的新详情；同水位下新的合法权限变化仍可生效。打开或重新载入取得的新详情立即更新原图区和对应缓存比赛行，不必等待轮询；切换到其他记录也不能让旧行重新开放上传，其他比赛仍保留各自权限。等待详情或心跳结束后，在下一次获取租约前重新核对打开上下文，已切离的记录不得继续发起新租约请求；当前记录的正常租约恢复保持。

小程序详情读取（包括原图加载失败后自动重新获取详情）、轮询及保存/校验/复核/警告确认/发布回包共同记录请求发起顺序。已知的同步摘要水位、已取得的完整正文及权限观察分别判断：摘要先报告新版本而保存正文仍在传输时，成功回包须补齐人工稿和后续操作版本，不能把旧正文标成已保存。真正随后提交并推进草稿或事件的写入也须接纳，但版本增长不代表旧请求中的角色权限更新；较新读取的能力不会被旧写回包恢复。旧正文不能覆盖已取得的新正文。较新读取成功后，旧轮询请求的失败不再覆盖当前错误状态；当前请求失败仍正常提示。后续新 GET 或轮询仍能采用合法的新授权，不把权限永久锁为禁止。能力刷新保留待保存人工输入、来源和 publication；不改变现有租约恢复或离页处理策略，也不新增原图重载按钮。

失败上传的幂等查询只读；当前权限、赛季、目标来源版本及图片一致性检查通过后才允许恢复暂存。拒绝重试不修改旧失败记录；已成功请求继续重放同一结果，不重复创建来源或审计。

## 状态与工作流

```text
上传完整单页原图
  -> RECOGNITION_QUEUED / RECOGNIZING
  -> RETRY_WAIT（如可重试）
  -> DRAFT 或 RECOGNITION_FAILED
  -> 人工编辑并保存
  -> 服务端校验、一次确认全部 warning
  -> READY
  -> PUBLISHED
```

`SOURCE_GAME`、`TEAM_A`、`TEAM_B`、`RUNNING_SCORE`、`SUMMARY`、`OFFICIALS` 只用于问题定位、识别差异和小程序步骤导航，不是电脑端发布前需要逐区点击的确认门槛。工作人员只保存能够确认的姓名；没有填写或看不清时保持为空，不再识别或人工选择签名状态。旧草稿和旧 publication 中的签名状态仅作为兼容字段保留。服务端会把前端整表自动保存拆成字段级变更日志。识别执行或等待自动重试期间所有客户端只读，且没有用户停止或重复启动接口；四次耗尽或凭据缺失后，普通管理员与超级管理员都可取得租约完整手工填写。未发布的失败记录可按下述明确覆盖流程发起新周期；名单缺失、图片非法等来源前置错误必须先修复来源。

## Qwen 识别与重试

识别 worker 使用 PostgreSQL 行锁、`skip_locked` 和五分钟 worker 租约，不依赖 Redis/Celery，也不在 Gunicorn 进程内执行模型请求。每个识别周期最多四次调用：首次加三次自动重试。满足下述条件并明确确认后，手动重试会创建新周期，不复用已耗尽的旧周期。

| 失败次数 | 下一次等待 |
| --- | --- |
| 第 1 次 | 30 秒 |
| 第 2 次 | 30 秒 |
| 第 3 次 | 30 秒 |
| 第 4 次 | 进入 `RECOGNITION_FAILED` |

网络错误、180 秒 SDK 网络读写超时、HTTP 429/5xx、服务商无效 JSON 和结果 Schema 错误可重试。服务商 `Retry-After` 更长时采用更长时间。来源缺失/替换、名单缺失、图片不合法、图片无法满足 Qwen Data URI 限制和凭据缺失不会重复调用。

发送给 Qwen 的内容严格限定为处理后的完整记录表，以及双方球队名称和球员姓名；不会发送账号、OpenID、UUID、球衣号码、赛季、日期、场地或其他比赛先验。8,000,000 像素只是小图放大目标，不是分辨率上限：小于目标时等比例放大且任一边最多两倍；达到目标的 JPEG/PNG 在无需 EXIF 纠正且完整 Data URI 未超限时保持原字节、分辨率和 MIME，WebP 在可直接传输的尺寸内同样保持原样，超过视觉服务尺寸边界时只转为同宽高 JPEG。不会主动缩小大图。

完整 Base64 Data URI 的十进制上限固定为 `20,000,000` 字节。超限时保持宽高不变、透明背景铺白，并在 JPEG 质量 1–95 中选择满足限制的最高质量；质量 1 仍无法满足时，以不可重试的 `IMAGE_DATA_URI_TOO_LARGE` 结束，不实例化 Qwen 客户端、不产生 token、也不进入后三次自动重试。原始上传文件始终原样保存在私有审计来源中，EXIF 纠正、放大和压缩只作用于 Qwen 临时副本。

默认使用 `qwen3.8-max`、`xhigh`、高分辨率视觉与 thinking、`seed=1234`、原版动态名单枚举 Schema 和严格结构校验。OpenAI SDK 的 `180` 秒参数是一次请求的网络读写超时，不是严格的总墙钟时限；超时按可重试错误处理。Worker 每分钟续期 PostgreSQL 五分钟任务租约，因此等待流式输出期间不会被其他 worker 重领。每个任务记录真实模型、提示词版本、最终发送图像 SHA-256、token、来源版本和入队草稿版本；来源被替换或任务已非当前周期时结果标记为 `SUPERSEDED`，不得写入当前草稿。

### 失败后的整稿重新识别（2026-08-28 决定）

- 仅当前来源的最新周期为 `FAILED` 且记录从未发布时允许重试；普通管理员和超级管理员相同。`SUCCEEDED` 不开放任意再识别，活动周期、归档及来源前置错误继续受原有保护。
- 已人工填写也可重试。网页和小程序必须先明确提示“成功覆盖整张草稿及人工修改，再次失败保留”，取消不保存、不入队；确认后先保存当前内容，再提交 `confirmed_overwrite=true`、版本、租约和稳定幂等键。
- 入队事务锁内重读当前权限、比赛、来源、草稿和最新任务，拒绝已有任何 publication 的记录（包括失败后纯手工发布、超管重新取得编辑权）。发布后的原图重传纠错仍是单独的既有超管工作流，不因此扩大权限。
- 入队前的完整草稿和身份映射保存在不可变修订。成功结果从干净文档生成并整稿覆盖，不沿用人工得分、教练、工作人员或旧识别结果；不建设新的差异/分区应用界面。再次失败不改变人工草稿、草稿版本或当前先验。
- 成功覆盖增加草稿版本，清空旧校验、警告确认和区域确认。旧显式球员映射不能套到新识别行；相关行需重新确认当前身份。原图、旧 recognition run、publication、revision 和审计不原地改写。
- Worker 在领取与结果落稿事务中再次核对当前来源/版本/周期和发布状态。入队后另有未被本次确认覆盖的新草稿变化时，不直接覆盖；来源、发布或任务已变化的迟到结果不得写入草稿。两端读取服务端 `can_retry`，不能仅凭持有租约推断可重试。

本地与生产环境变量：

```dotenv
QWEN_API_KEY=
QWEN_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
QWEN_MODEL=qwen3.8-max
QWEN_REASONING_EFFORT=xhigh
SCORESHEET_RECOGNITION_UPSCALE_TARGET_PIXELS=8000000
SCORESHEET_RECOGNITION_TIMEOUT_SECONDS=180
```

`scripts/deploy-wsl.ps1` 获取密钥时依次使用当前 Windows 进程/系统环境中的 `QWEN_API_KEY`、项目私有 `.env`、已有 `.env.wsl.local`，并把最终值写入被 Git 忽略的 `.env.wsl.local`。`check-api.sh` 与 `pytest-api.sh` 只通过容器环境传递该配置，不打印密钥。普通回归默认使用 Mock；只有显式启用真实识别验收时才会产生 Qwen 调用与费用。

未配置 `QWEN_API_KEY` 时，worker 会把任务一次性标记为不可重试失败，页面仍可进入人工录入。生产 worker：

```bash
python manage.py process_scoresheets --poll-seconds 2
```

## 编辑租约与两秒同步

- 有写权限时打开编辑器取得 60 秒租约；自动识别执行或等待重试时所有人只读，终态成功、耗尽失败或凭据缺失后按权限自动取得租约，网页和小程序每 15 秒心跳。归档纠错租约另存服务端授权标记，归档前取得的普通租约不能在归档后继续写入。
- 同一时刻只有租约持有账号、客户端 ID 和端类型可写。网页每个标签页使用独立 `sessionStorage client_id` 和租约令牌，同一标签页刷新可恢复，不同标签页互不轮换令牌。获取、心跳、同步和释放均使用单飞锁；其他端每 2 秒轮询并保持只读。
- 保存、校验、warning 确认和发布都提交 `expected_version`、`lease_token`、`client_id`、`surface`。
- 两端不显示“接手、交接、强制接管”按钮。首个打开且有权限的终端自动取得编辑权；正常返回和发布先排空自动保存再释放，租约释放或 60 秒失效后，仍在前台的只读端在下一轮同步中自动取得编辑权。
- 服务端仍严格拒绝旧 token；超级管理员的已发布纠错权限和强制接管审计能力保留为受保护的服务能力，不在普通编辑界面暴露手工租约控制。
- 回到前台或网络恢复时立即同步。若本地草稿所基于的服务器版本未变化，可重新取得租约后恢复保存；若已变化，两端列出差异字段并要求明确选择服务器值或本地值。
- 撤销/重做作为普通服务端修改保存。网页保留最近 50 步会话历史；本地历史本身不替代服务端修订。
- 编辑器“人工修改记录”只返回人工编辑、撤销、重做、应用识别差异、重传和发布，并以中文摘要、稳定语义路径以及真实“修改前 → 修改后”值展示。得分格使用“A/B 队 + 累计分”作为稳定身份，人工记录只展示所选号码；自动派生的分值、节次、符号、颜色、序号、边界和最终结果仍进入跨端同步与系统审计，但不计作人工修改。租约、心跳、过期、识别 worker、校验和同步事件仍保留在数据库和高级数据页，不进入该列表；历史记录不删除，也不补造早期未保存的修改前值。

## 编辑器

电脑端从比赛资料进入独立的全视口 `scoresheet.html`，完整保留冻结版 `ScoresheetReader` 的布局、字段编辑、覆盖层、原图/PDF 对照、缩放旋转、检查器、撤销重做、识别差异、保存、校验和确认交互。PKUBA 适配层只替换数据与认证接口，并补入自动租约、750 ms 自动保存和两秒同步，不重新设计其编辑操作。

小程序编辑器位于独立分包，不使用 PDF.js 或 `web-view`，使用微信原生导航栏，不再自绘沉浸式全屏标题栏。步骤精简为“比赛、A 队、B 队、得分、结表、发布”，原图/标准表是当前步骤内的单视图切换。页面根节点固定为视口高度：标准表每个步骤使用一个明确高度的纵向滚动面，逐次得分页只允许得分格列表纵向滚动，底部操作栏不覆盖内容。原图由 `MovableArea/MovableView` 独占手势，支持双指缩放、横向/纵向/斜向拖动、旋转和复位，不采集角点、不显示定位框，也不修改已有 `source.corners`。赛事、日期、开赛时间、场地和球队名称来自赛程/名单快照；小程序仅展示有业务含义的只读项，不显示内部比赛编号、UUID、哈希、publication 号、草稿版本或识别尝试编号。

逐次得分按 `1-40`、`41-80`、`81-120`、`121-160` 四块显示。每一格都可点选：空格只选择本队名单球衣号，已有号码只能换人或清空。中间插入和删除不会移动其他累计格。分值由同队前一已填累计格推导，节次及节末/终场标记由书面节比分累计检查点推导，得分符号和序号随之生成；客户端不能修改这些派生字段，服务端在保存和应用识别结果时重新规范化。推导值达到 4 分及以上时以红框保留草稿，但服务端校验阻止发布。

节次只有第 1–4 节与可选的第 5 节；第 5 节表示所有实际加时的合计，不保存 OT1/OT2 等中间分段。服务端明确拒绝同队重复累计格（`DUPLICATE_SCORE_CELL`）、单次得分跨过书面节末检查点（`SCORE_EVENT_CROSSES_PERIOD_BOUNDARY`）和检查点所在固定格缺少事件（`PERIOD_BOUNDARY_WITHOUT_EVENT`）。

球队暂停、全队犯规和各节比分使用加减按钮；球员及教练犯规使用与电脑端相同的 FIBA 2024 受限选项，包含下标 `1/2/3`、`Pc` 等抵消写法和正式格后 `D/GD/F` 标记，不接受自由文本。最终比分为各节书面比分之和，胜队随之派生，两个端都不能直接修改；结束时间使用时间选择器。两端始终显示“记录台人员 · 不分岗位”姓名列表，无识别结果时也能人工增删；服务端用专用人工承载标记保存该列表，不把它误判为一次识别结果，明确角色人员继续分别填写姓名。

## 校验与发布事务

发布前同时检查：

- 当前来源、草稿、名单先验和比赛先验与校验报告摘要一致；
- error 为零；如存在 warning，发布前只弹出一次确认，确认后服务端一次性记录当前全部 warning；
- 当前客户端仍持有租约；
- 逐次得分、纸面累计、逐节比分和最终比分一致，正式比分不为平局；
- 冻结名单、首发/出场、队长、犯规、暂停、全队犯规、自动派生的终场标记和工作人员字段满足当前 Schema/FIBA 2024 规则。

单一数据库事务创建不可变 `ScoresheetPublication`、`GameTeamStat`、`GamePlayerStat`，更新比赛正式比分和状态，把来源标为已通过，写修订/变更/管理员审计并释放租约。任一步失败都会回滚。弃权继续使用既有超级管理员 20:0 流程，不创建普通记录表 publication。

首次发布自身递增的 `Game.version` 会同步回记录表比赛先验；它不是比赛语义版本。原样保存、仅修改调赛政策、申请建立或撤回等没有改变比赛信息的操作，不要求重传原图；重新校验后按既有权限发布。已有 publication 的比赛不能再从通用赛程编辑器直接改比分或赛果，必须从记录表工作台重新发布。公开页与 CSV/XLSX 始终读取当前 publication 的快照名称、比分和统计，不读取以后可能变化的 `Game` 分数或球队名称。

### 比赛信息变化后的受控复核

校验和发布都在事务内重新读取并锁定当前比赛及名单。比较赛季/组别、双方稳定身份与名称、日期、实际时间、标准时段、场地、阶段/轮次/小组和启用名单/参赛资格，而非只比较 `Game.version`。

- 信息未变：保留原图及人工草稿，重新校验即可；不触发 Qwen 或重传。
- 信息确有变化：校验报告返回人类可读的前后差异；网页检查器和小程序“发布”步骤展示“核对比赛信息变化”。有写权限的管理员对照原图确认后，只更新当前比赛先验和只读抬头，保留得分、犯规、工作人员等人工内容。
- 旧快照缺少时段等关联依据：要求一次明确复核，不默默补齐；复核后的只读 GET 不再写入或反复要求确认。
- 球队或球员身份已变：不能把旧数据自动转给同名新身份。管理员逐行选择当前可参赛名单，或修正球员行；未解决、非当前名单、不可参赛或重复绑定仍阻止发布。球衣号码属于本场，不能单靠旧号码分配积分。
- 已明确确认的球员使用稳定 ID：仅修改该行的本场号码，不会解除绑定或把得分转给另一位同名球员。绑定身份被停用、姓名变化或不再具备参赛资格时，仍要求重新核对。
- 复核令牌有效期 10 分钟，绑定记录、来源资产/版本、草稿版本/摘要、旧先验/名单和当前语义摘要。任何二次变化、跨记录或跨来源重用返回 `409`，保留草稿；重新校验后再复核。复核请求使用同一个 `Idempotency-Key` 重试不重复创建修订/审计。
- `POST /api/v1/scoresheets/{id}/game-context/review` 需要有效编辑租约、显式确认和当前权限。首次发布前两类管理员均可复核；已有 publication 仅超级管理员。归档只沿用 WEB 有效超管、逐记录确认、已有 publication 的窄纠错例外，小程序仍只读。
- 原图、识别 run/notes/problem_paths/applied_at、旧 publication/revision 不被复核重写。复核前后各留下不可变修订及 `SCORESHEET_GAME_CONTEXT_REVIEWED` 审计；当前先验与上传/识别时的历史来源证据分开保存。确认不等于通过校验，之后仍重新执行名单、比分、警告和发布事务保护。
- 网页复核、后续校验与历史请求绑定本次打开代次及来源/草稿快照。切换记录或重新打开同一记录后，旧请求的成功、失败和结束状态均不得覆盖新页面内容或忙碌状态。

## 公开统计与导出

公开数据只来自当前 publication：

- 球队：逐节/全场得分、胜负、暂停和全队犯规。
- 球员：出场、首发、得分、1/2/3 分事件数、个人犯规数及类型。

不推导命中率、篮板、助攻、抢断、盖帽、失误、上场时间或正负值。管理员编辑器的 PDF 始终渲染当前服务端草稿（包括已发布后的未再发布纠错）；公众展示和单场 CSV/赛季 XLSX 始终读取当前 publication。

## 本地双端编辑演示数据

`ScoresheetReader` 仓库没有可迁移的真实比赛原图或私有识别结果；可复用的数据是其公开合成测试夹具。新版提供一个显式、幂等的管理命令，把这份夹具转换为当前 Schema，并生成一张与其对应的纸面式 JPEG：

```bash
python manage.py seed_scoresheet_demo --confirm-local-demo --actor <superadmin-username>
```

命令只创建非公开的 `PKUBA 记录表编辑器演示` 赛季，不切换、归档或修改当前公开赛季。为了让真实租约和保存服务可用，它会把该隔离赛季的唯一演示组别标记为可操作；这是显式命令创建的本地测试例外，不是正式赛季上线流程。演示比赛固定显示为“示例学院甲 vs 示例学院乙”，开赛时间为 `12:50`；草稿直接移植公开 `synthetic_fixture.py` 的 1.4 语义，包含双方各 12 人、执照号、正式及纸面后置犯规、暂停、19 条逐次得分、四节比分、最终 `21:18` 和工作人员姓名。兼容签名字段统一保持 `absent`，界面不展示。识别任务按一次成功写入相同的 revision、事件和审计链，适合在网页和小程序之间实际测试自动只读、自动取得编辑权、保存、两秒同步、校验和发布。

默认管理员记录表队列继续列出公开赛季全部比赛，同时会额外列出已有记录表的非公开演示比赛；没有记录表的其他非公开赛季比赛不会混入队列。小程序卡片只展示日期、开赛时间、组别和双方，不展示内部比赛代码或 UUID。

## 私有文件、导出与备份

记录表、比赛合照和其他照片全部按块写入安全临时文件，同时累计真实字节数和 SHA-256，再由 Pillow 从路径验证 JPEG/PNG/WebP、尺寸与 EXIF。应用层不再按文件字节数主动拒绝，也不设置自定义解码像素上限；Pillow 的解压炸弹 Warning/Error 都作为 413 安全错误。原始上传文件原样保存，格式失败、存储失败、数据库冲突和幂等重放都必须清理临时文件及未引用存储对象。所谓“无上传大小限制”不等于无限资源：600 秒 HTTP 请求时限、微信/浏览器客户端能力、磁盘容量与 Pillow 安全保护仍是运行边界。

当前部署长期使用 Django `default_storage` 的私有本地 Docker volume，不接入腾讯 COS；文件只能通过短期签名票据接口读取。PostgreSQL 与私有媒体必须作为同一恢复点，不能只备份数据库：publication 会保留来源外键，但缺少对应文件时将无法查看已发布原图或重新识别。

超级管理员可分别导出赛季结构化数据、赛季全部照片和未加密全系统原始备份。归档赛季在最终数据/照片包完整并确认线下保存后，可永久删除服务器上的记录表、比赛合照、其他照片及历史版本；数据库媒体行、文件哈希、publication 来源、历史修订和审计仍永久保留。已清理文件读取返回 `410 MEDIA_PURGED`，界面不得显示破图。

三类包格式、24 小时暂存、磁盘预检、照片清理前置条件、阿里云日备覆盖和 `restore_system_backup` 隔离恢复步骤统一见 [`docs/BACKUP_AND_ARCHIVE.md`](BACKUP_AND_ARCHIVE.md)。不要在生产库或当前媒体卷上直接演练恢复。
